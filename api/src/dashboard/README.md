# dashboard (เซิ่น)

แดชบอร์ดและรายงาน — endpoint sheet แถว 95-100

> โค้ดในโมดูลนี้ไม่มี comment ในไฟล์โดยตั้งใจ — เหตุผลเบื้องหลังทุกอย่างอยู่ใน README นี้

โมดูลนี้เป็น **read model** ล้วนๆ ไม่เขียนอะไรลงฐานข้อมูลเลยสักที่
และอ่านตารางของโมดูลอื่นเป็นหลัก (`sales`, `sale_items` ของพี่ดิว)
ถ้าเจ้าของตารางเปลี่ยนโครงสร้าง query ที่นี่จะพังโดยไม่มีอะไรเตือน
เทสต์ในโมดูลนี้จึงคลุมทุก query ที่ยิงออกไป

## แพ็กเกจ — ทำไมแถว 97/98 ถึงไม่ใช่ของ Free

ชีทจัดสองแถวนี้ไว้กลุ่ม `Dashboard` แต่ **ยึดตาม SRS** ซึ่งเขียนว่า
"Free Plan จะเห็นได้เฉพาะสรุปยอดขายรวมแบบพื้นฐานเท่านั้น" และนิยาม Advanced Reports
ว่ารวม "เปรียบเทียบสินค้า/หมวดหมู่" — การจัดอันดับสินค้าขายดีก็คือการเปรียบเทียบสินค้า

ตกลงกับทีมแล้วว่าใช้ SRS เป็นหลัก และ**ย้ายแถว 97/98 ในชีทไปกลุ่ม Advanced Reports แล้ว**

เช็คด้วย `subscription_plans.isFree` ไม่ได้เพิ่มคอลัมน์ใหม่ เพราะ SRS แบ่งแค่ Free กับ Paid

ตอบ `403` พร้อม `code: PLAN_UPGRADE_REQUIRED` และ `requiredPlan` **ไม่ใช่ซ่อน endpoint ทิ้ง**
เพื่อให้หน้าเว็บขึ้นการ์ดชวนอัปเกรดได้ ตามที่ SRS สั่งไว้ตอนโควตาสินค้าเต็มว่า
"ต้องแสดงข้อความแนะนำให้อัปเกรดแพ็กเกจ"

## สิทธิ์

`DashboardAccessService` ห่อของที่มีอยู่แล้วสองตัว ไม่ได้เขียนด่านใหม่

| ตรวจอะไร                                                           | ใช้ของใคร                         |
| ------------------------------------------------------------------ | --------------------------------- |
| ร้านเป็นของ owner นี้ไหม / พนักงานถูก assign ไหม / ร้านถูกระงับไหม | `PrismaShopAccessAdapter` (เซิ่น) |
| `staff_permissions.can_view_dashboard`                             | `staff_permissions` (อั้ม)        |
| `subscription_plans.is_free`                                       | `subscription_plans` (พี่ปาน)     |

**เจ้าของร้านข้ามด่าน `canViewDashboard`** — สิทธิ์รายบุคคลมีไว้จำกัดพนักงานเท่านั้น

ใช้ `@CurrentUser('sub')` ไม่ใช่ `@OwnerId()` ด้วยเหตุผลเดียวกับ `products` —
โมดูลนี้ต้องรู้ว่าใครเป็นคนยิงเพื่อเทียบกับ `staff_permissions` ถ้าใช้ `@OwnerId()`
พนักงานจะ resolve เป็นเจ้าของร้าน แล้ว `isStaff` เป็น `false` ตลอด ด่านสิทธิ์จะถูกข้าม

**ไม่เรียก `assertNotReadOnly()`** — SRS บอกว่าแพ็กเกจหมดอายุแล้ว "ดูข้อมูลได้อย่างเดียว"
ซึ่งแดชบอร์ดคือการดูล้วนๆ จึงต้องเปิดให้ดูได้ต่อ

## กติกาที่ใช้ทุก endpoint

- **นับเฉพาะบิล `COMPLETED`** บิล `VOIDED` ถูกคืนสต็อกไปแล้ว ถ้ายังนับยอดจะบวมเกินจริง
- **แสดงกำไรขั้นต้น ไม่ใช่กำไรสุทธิ** ตัวเลข `grossProfit` คือ ยอดขาย − ต้นทุนของ
  ที่ขายไป ไม่ได้หักค่าเช่า ค่าแรง หรือค่าน้ำค่าไฟ ฝั่งหน้าเว็บต้องเขียนป้ายให้ตรง
  ห้ามใช้คำว่า "กำไร" ลอยๆ
- **ต้นทุนอ่านจาก `sale_items.cost_price` เท่านั้น** ห้ามย้อนไปอ่าน
  `shop_products.cost_price` ปัจจุบัน โมดูล sales snapshot ทุนไว้ตอนเปิดบิลแล้ว
  (`prisma-sales-adapters.ts`) ถ้าเจ้าของร้านขึ้นราคาทุนทีหลัง กำไรของบิลเก่า
  ต้องไม่ขยับตาม เหตุผลเดียวกับที่ best-sellers อ่านชื่อจาก snapshot
- **`itemsWithoutCost` ต้องส่งไปด้วยเสมอ** `cost_price` มี default 0 และหน้าเพิ่ม
  สินค้าไม่บังคับกรอกทุน สินค้าที่ปล่อยว่างจะดูเหมือนกำไร 100% หน้าเว็บจึงต้อง
  เตือนได้ว่าตัวเลขยังไม่ครบ ไม่ใช่ปล่อยให้อ่านผิด
  (หมายเหตุเดิมในไฟล์นี้เขียนว่า "ไม่แสดงกำไร เพราะ SaleItem ไม่มีฟิลด์ทุน" —
  ตกยุคแล้ว โมดูล sales เพิ่ม `cost_price` เข้ามาภายหลัง)
- **ไม่ส่ง `from`/`to` มา = 30 วันล่าสุด** ช่วงสูงสุด 365 วัน เกินกว่านั้นตอบ 400
- **สินค้าที่ถูก soft delete ไม่ปรากฏ** กรอง `product.deletedAt = null` ทุก query

## best-sellers ใช้ชื่อสินค้าจาก snapshot

อ่าน `sale_items.productName` ตรงๆ **ไม่ join กลับไป `shop_products`**
เพราะชื่อกับราคาสินค้าเปลี่ยนได้ รายงานย้อนหลังต้องแสดงชื่อ ณ ตอนที่ขาย
DBML เขียนเตือนเรื่องนี้ไว้ว่าเป็น "บั๊กที่พบบ่อยที่สุดในระบบ POS"

## dead-stock

นิยาม: `status = ACTIVE` และ `stockQty > 0` และไม่มี `sale_item` ของบิล `COMPLETED`
ภายใน N วัน (`?days` ค่าเริ่มต้น 30 รับ 7–365)

เรียงของที่**ไม่เคยขายเลยขึ้นก่อน** แล้วตามด้วยที่นานที่สุด — สินค้าที่ไม่เคยขายเลย
คือของที่ค้างหนักที่สุด ถ้าเรียงตามจำนวนวันเฉยๆ มันจะได้ `null` แล้วตกไปท้ายลิสต์

`lastSoldAt: null` แปลว่าไม่เคยขายเลย ไม่ใช่ "ไม่มีข้อมูล"

query แยกเป็นสองรอบโดยตั้งใจ — รอบแรกหาว่าตัวไหน**เพิ่งขาย**เพื่อคัดออก
รอบสองหาวันที่ขายล่าสุดเฉพาะตัวที่เหลือ ถ้ารวมเป็นรอบเดียวจะต้องดึงประวัติการขาย
ทั้งหมดของทุกสินค้ามาก่อนแล้วค่อยกรอง ซึ่งโตตามจำนวนบิลไม่ใช่จำนวนสินค้า

## summary — ร้านที่พนักงานเห็น

`listVisibleShopIds()` เป็นตัวตัดสินว่ารวมร้านไหนบ้าง

- **เจ้าของร้าน** เห็นทุกร้านของตัวเองที่ยังไม่ถูกลบและไม่ถูกระงับ
- **พนักงาน** เห็นเฉพาะร้านที่ถูก assign **และ**เปิด `canViewDashboard` ให้ในร้านนั้น

พนักงานที่ไม่ได้ถูก assign ร้านไหนเลยได้ลิสต์ว่าง ไม่ใช่ 403 — เพราะไม่ใช่เรื่องสิทธิ์
แต่เป็นเรื่องไม่มีข้อมูลจะแสดง และไม่ยิง query ต่อเลยเมื่อลิสต์ว่าง

ร้านที่ไม่มีบิลในช่วงเวลาที่เลือก**ยังอยู่ในลิสต์ด้วยยอด 0** ไม่ตัดทิ้ง เพื่อให้หน้าเว็บ
เห็นว่าร้านนั้นเงียบ ไม่ใช่หายไปเฉยๆ

## sales-trend — เรื่อง timezone

`Sale.createdAt` ประกาศเป็น `DateTime` เฉยๆ **ไม่มี `@db.Timestamptz(6)`**
ต่างจาก `shop_products` กับ `notifications` แปลว่าคอลัมน์เป็น timestamp ที่ไม่มี timezone
ติดมาด้วย Prisma เขียนลงเป็น UTC

การจัดกลุ่มรายวันจึงต้องแปลงเป็นเวลาไทยก่อนเสมอ ไม่งั้นบิลที่ขายตอนเช้า 7 โมง
จะไปนับเป็นของเมื่อวาน คำนวณด้วย offset คงที่ `UTC+7` ใน `period.util.ts`
ประเทศไทยไม่มี DST จึงไม่ต้องใช้ไลบรารี timezone

**ข้อควรรู้สำหรับคนเรียก** — `from`/`to` ที่ส่งมาเป็น UTC ถ้าอยากได้ช่วงที่ตรงขอบวันไทย
ต้องส่ง `2026-07-31T17:00:00Z` แทน `2026-08-01T00:00:00Z`

ส่วนการแก้ชนิดคอลัมน์เป็นของโมดูล sales ไม่ใช่ของโมดูลนี้ — ฝากพี่ดิวพิจารณา

## sales-trend — ทำไมไม่ใช้ SQL `date_trunc`

จัดกลุ่มในโค้ดแทนการยิง raw SQL เพราะสามเหตุผล

1. `date_trunc` บน timestamp ที่ไม่มี timezone ต้องเขียน
   `created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Bangkok'` ซึ่งเขียนผิดง่ายมาก
   และผิดแบบเงียบๆ ไม่ error
2. raw SQL เทสต์ด้วย mock ไม่ได้ ต้องมี Postgres จริงถึงจะรู้ว่าถูก
   ซึ่งขัดกับที่ทั้ง repo เทสต์ด้วย mock ล้วน
3. ช่วงเวลาถูกจำกัดไว้ที่ 365 วันอยู่แล้ว จำนวนแถวจึงมีเพดาน

**แลกมาด้วย** — ดึงแถวบิลในช่วงนั้นมาทั้งหมด (เฉพาะ 2 คอลัมน์) แล้วนับในหน่วยความจำ
ร้านที่ขายวันละหลายพันบิลจะเริ่มหนัก ถ้าถึงจุดนั้นค่อยย้ายไป `date_trunc` พร้อมเทสต์
ที่ต่อ Postgres จริง

ช่วงที่ไม่มียอดขายคืนจุดที่เป็น `0` **ไม่ข้าม** เพื่อให้กราฟฝั่งเว็บไม่ขาดช่วง

## by-category

SRS ระบุว่า "เปรียบเทียบสินค้า/หมวดหมู่" เป็นส่วนหนึ่งของ Advanced Reports
แต่ชีทเดิมไม่มี endpoint นี้เลย **เพิ่มแถว 100 เข้าไปในชีทแล้ว**

`shareOfTotal` เป็นสัดส่วนต่อยอดรวมในช่วงเวลานั้น (0–1 ปัดทศนิยม 4 ตำแหน่ง)
ให้หน้าเว็บเอาไปทำกราฟวงกลมได้โดยไม่ต้องคำนวณเอง

**สินค้าที่ไม่มีหมวดหมู่รวมเป็นกลุ่ม `categoryId: null` ไม่ตัดทิ้ง** —
`products.category_id` เป็น nullable และ relation เป็น `onDelete: SetNull`
แปลว่าลบหมวดหมู่แล้วสินค้าจะกลายเป็นไม่มีหมวดทันที ถ้าตัดกลุ่มนี้ทิ้ง
ผลรวมของทุกหมวดจะไม่เท่ากับยอดขายจริง ซึ่งคนอ่านรายงานจะจับได้ทันทีว่าตัวเลขไม่ตรง

จัดกลุ่มในโค้ดด้วยเหตุผลเดียวกับ `sales-trend` — Prisma `groupBy` จัดกลุ่มตาม
field ของ relation ข้ามชั้นไม่ได้ (`sale_items` → `shop_products` → `products.category_id`)
ต้อง groupBy ที่ระดับ `shopProductId` ก่อนแล้วค่อยยุบเป็นหมวดหมู่ในหน่วยความจำ
จำนวนแถวมีเพดานเท่ากับจำนวนสินค้าในร้าน ไม่ใช่จำนวนบิล

## ที่ยังไม่ได้ทำ

- ยังไม่มี cache — ทุก request ยิง query จริงทั้งหมด ถ้าร้านโตจนช้าค่อยว่ากัน
